# 2026-09-30 列连续矩阵 Eigen 优化（局部进展）

## 变更与设计

基线 `580359f9e61847d5794efb3edbc0b3ae513e3a059c7e705be239ca6374192549`；正式构建 `0ddf9e4e4edf2dc1fa50326e8e01fc1a2a0a21689d13a16b84c4a13cc0e590aa`。复用现有 Eigen 3.4，不新增依赖。

- `sum_axis/mean_axis/variance_axis(X,0)`：用固定8列借用Map跨独立列计算，保留每列递增行序、两遍方差、ddof、非有限规则及逐列失败写入前缀。sum/mean不增加有限性校验。适用 macOS15+ arm64、Eigen开启、非scalar、至少32行/8列、行stride为1且列pitch不小于行数；补边列距可用。
- 既有混合图的双算子融合：第一步add/subtract/multiply接列连续矩阵与标量/列广播参数，第二步接另一标量/列广播参数。Eigen负责8行块算术，每16行分块，直接写独立C序结果。保持运算与操作数顺序；中间值作除数或广播除数含零，在任何写入前转原有路径。原单消费者、非根中间值及持久输入/root后备等融合限制未扩大。
- 没有新数值堆、输入打包、私有线程或跨请求缓存；不改AST/DAG数学、Planner、IPC、结果所有权或Excel公式/预算。复用的是公共Array/Map表达式，项目仍控制保序遍历，不能称为直接使用默认矩阵归约/GEMM。

[详细设计](production-design.md)与[正式对象检查](object-review.json)：latent/foundation共同帧1088/752B保持不变，先恢复再尾调用224B方差、32B均值或128B求和叶子。算术wrapper48B+准入64B，随后释放wrapper再尾调用320B Eigen或480B原标量执行；Eigen尾行可调用48B scalar_math，自有正常链峰368B，小于旧480B。新算术内核无FMA。系统/运行库/异常栈未完整定界，不能把这些数字当整个请求栈峰。

## 内存与未完成项

8用例、48个独立内存子进程；冷/暖分开，六个heap阶段、七字段旧新逐项相同。没有探针表溢出。归约暖堆仍比NJIT多13,856B框架开销；标准化两种规模暖堆多27,294/28,382B。数值工作区为零不代表整个请求无分配，也不能据此宣称内存优于NJIT。

RSS总峰5/8正差，请求增量5/8正差，最大请求增量正差81,920B。跟踪堆相同不等于完整RSS不增；本轮完整内存条件仍开放。8个额外诊断进程将64列代表用例的表外释放定位到测量前已记录的NumPy维度分配：三类归约各2×16B，标准化5×16B，无未见来源。此诊断只解释这些计数，不解释RSS差；不与正式时间/RSS混用，也不冒充全进程全分配覆盖。

下一步仍需解决标准化F输入到C结果的访问效率、C小矩阵控制退化原因，以及普通请求的固定分配与RSS。全185算子的全面时间/内存目标未达成。本轮仅本地修改，未提交或推送，未改研究平台。
