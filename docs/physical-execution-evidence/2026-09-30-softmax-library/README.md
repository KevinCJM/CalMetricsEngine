## 实现与数学边界

macOS15+ arm64、固定Eigen3.4、非scalar、总元素≥256、轴长度≥8、输入轴stride=1且输出轴inner=1时，独立行driver借用输入，并将公共Eigen Array指数直接写入原独立结果。逐元素升序求和，再做真实除法，不创建数值工作区、打包数组、私有线程或跨请求状态。每行先完成finite/max/min；只有 `min-max >= log(count)-700` 才走库，避免Eigen的-709.784截断及归一化下溢。其余行、布局、平台和Eigen-OFF保持原数学路径。指数多项式有显式FMA，原容差与离散结果检查均保留；不宣称逐位相同。

算子签名、AST/DAG、Planner、结果所有权、错误隔离、IPC和Excel公式/预算不变。详细依据见[设计](production-design.md)。库driver最终独立于原通用axis模板，模板恢复时核对了变更前文件SHA。

## 内存与审核

8项普通入口、48独立heap/RSS子进程：六阶段七字段的旧/新跟踪heap逐项一致，无表溢出或unknown free。请求RSS增量新−旧全部≤0；进程总RSS峰仍有4/8正差，最大+638,976B，基线RSS也不同，不能将两种口径混用或宣称全部驻留内存不增。对NJIT，冷/暖heap固定多13,582/13,944B；总RSS峰均低，但请求RSS增量5/8较高，最大+4,784,128B。因此“全部中大型时间、内存都明显优于NJIT”仍未达到。

V1局部栈640B；V2拆行helper后432B。V3通用axis恢复原224B，库driver272B+helper192B=464B；latent入口仍1088B且真实tailcall，不与数值链叠加。库局部链仍比原核大240B，系统exp/log及异常/外层栈未穷尽，不能用workspace=0替代完整内存结论。正式对象与独立审查对象逐字节一致，详见[对象审核](object-review.md)。静态同行审核覆盖不变的库helper、guard、所有权和性能脚本；V3分派及循环由主代理复核并重新执行全部验证。

另用6个诊断子进程定位**前轮协方差联合请求**的unknown frees：每联合请求4×16B+1×32B，全为epoch0的NumPy维度/stride缓存，分配/释放PC已与实际二进制对应。它解释原计数，不解释数MiB RSS，也不表示全分配入口均覆盖。[地址归因](allocation-trace.md)。空status_owner的小分配补丁仅写于临时目录，未混入此轮实现。

## 失败候选与复现

未保护的Eigen指数原型在2,448记录中有198项零值分类失败，保留原始记录；保守span700原型2,736项通过后，正式实现进一步收紧为count-adjusted guard。V2虽通过正确性测试，但完整F控制曾明显回退，因此拆出独立driver形成V3；V2时间数据保留，未作为最终结果。一次过早执行身份校验因Excel快照报告尚未生成而失败，待原进程正常结束后校验成功，没有因此重启数值任务。
